# 插图生成策略讨论

> 讨论日期：2026-07-05
> 背景：已具备两套生图方案（PuLID SDXL + Agnes AI），现在需要确定"一卷小说到底在哪里生成插图、生成多少张"
>
> ⚠️ **核心约束：本项目是通用小说处理项目，不是针对某部小说的定制工具。**
>
> 这意味着：
> - 代码中不能硬编码特定小说、角色、场景的名称或特征
> - 不能针对某一类型小说（如轻小说、奇幻、言情）做特定优化
> - 所有分析逻辑必须基于文本本身，而不是预设的角色知识
> - 角色信息全部来自用户输入的 `docs/角色卡.md`，不从 prompt 或代码中内置
> - 同一套代码换一本小说应该同样工作，不需要改代码

---

## 一、问题本质

不是"多少对话出一张图"的简单规则——而是**让 AI 理解叙事结构，在关键节点自动配图**。

比如第一卷开头：
```
罗伦斯和村民交易小麦 → 只需要 1 张图（概括交易场景）
「怎么回事？」→ 骑士招手、罗伦斯疑惑 → 需要 1 张图（角色反应）
```

同样一段文本，插图的密度和位置取决于**叙事节奏**，而不是字符数或对话数。

---

## 二、跟 BGM 流水线的类比

BGM 流水线（`bgm_segmenter.py`）的做法是**多轮 Agent 对话**，不是一次完事：

```
调用方式	        说明
─────────────────────────────────────────────────
segment_novel()	        工具调用模式
                          LLM 可以反复调用工具分段阅读小说
                          提交/调整/删除分段，满意后才 finish
                          上限 80 步，实际 10-30 轮

segment_novel_chunked()	多 Agent 分块模式
                          拆成 6 块，每块独立调 LLM 分析
                          然后合并、去重、补间隙

label_bgm_types()	        批量标注
                          每 50 段一批，每批一次 LLM 调用
```

插图生成可以借鉴同样的思路，但需要更精细的判断：

| BGM 流水线 | 插图流水线 |
|-----------|-----------|
| 多次 LLM 调用（工具/分块） | 同样需要多次调用 |
| 场景分割 + 情感标注 | 场景分割 + 关键帧识别 |
| 每段一个 BGM 类型 | 部分场景配图，部分不配 |
| BGM 持续播放 | 插图是离散的"快照" |
| 情感决定 BGM 风格 | 情感 + 叙事重要性决定是否配图 |

## 三、插图应该放在哪里

### 3.1 适合配图的位置

| 场景类型 | 例子 | 配图优先级 |
|---------|------|-----------|
| **角色首次登场** | 赫萝第一次出现在麦田里 | ⭐⭐⭐⭐⭐ 必配 |
| **重大事件转折** | 发现阴谋、决定去某地 | ⭐⭐⭐⭐⭐ 必配 |
| **情感高潮** | 感人对话、激烈争吵 | ⭐⭐⭐⭐ |
| **场景转换** | 从村庄到城镇、白天到夜晚 | ⭐⭐⭐⭐ |
| **关键对话** | 揭露真相、重要交易 | ⭐⭐⭐ |
| **战斗/动作场面** | 冲突、追逐 | ⭐⭐⭐ |
| **日常过渡** | 走路、吃饭、普通对话 | ⭐ 不配 |

### 3.2 不适合配图的位置

- 纯叙述性过渡段落（"他们走了三天后..."）
- 连续快速对话（信息交换，无画面感）
- 内心独白（无视觉元素）

### 3.3 密度参考

| 章节长度 | 建议插图数 | 说明 |
|---------|-----------|------|
| 短（~2000 字） | 1-2 张 | 关键场景即可 |
| 中（~5000 字） | 2-4 张 | 开场 + 高潮 + 结尾 |
| 长（~10000+ 字） | 3-6 张 | 开场 + 每个关键转折 + 结尾 |

## 四、两阶段策略

插图生成必须分两个完全独立的阶段，不能混在一起。

### 第一阶段：分析决策（先做，我们手动验证）

只调用 LLM，不调用生图 API。目标是产出一份"插图计划"。

**工作方式：**
- LLM 通过工具调用（tool calling）自由阅读小说，自己决定每次读多少、读哪段
- 不限制每次读多少行（让模型自己判断），也不批量喂入
- 模型可以反复调用工具，像 BGM 的 `segment_novel()` 一样多轮迭代
- 支持提交、调整、删除插图决策
- 每次调用的模型名、tokens 消耗（prompt + completion）都要记录，便于后续 debug

**产出：插图计划 JSON**

```json
{
  "illustrations": [
    {
      "scene_index": 1,
      "start_line": 1,
      "end_line": 30,
      "scene_type": "character_intro",
      "description": "罗伦斯在村庄集市与村民交易小麦",
      "characters": ["罗伦斯"],
      "composition": "中景，罗伦斯站在摊位前，周围是村民和货物",
      "prompt": "a young male merchant with short brown hair, medieval traveler cloak, standing at a market stall bargaining with villagers, sacks of wheat visible, sunny village square, anime style, masterpiece"
    }
  ]
}
```

**质量要求：**
- 不追求速度，只追求质量，API 管够
- 我们手动审查插图计划，确认位置和 prompt 是否合理

### 第二阶段：生图（等第一阶段通过审查后再做）

输入插图计划，逐条调用生图 API 实际生成图片。

- 有角色参考图 → PuLID（角色一致性更好）
- 无参考图或批量场景 → Agnes（免费无限）
- 每张图独立调用

## 五、角色一致性问题

插图涉及角色时，需要决定用哪张参考图：

| 情况 | 处理 |
|------|------|
| 角色首次登场 | 需要参考图（用户提供），后续复用 |
| 角色已登场过 | 复用已有参考图 |
| 多角色同场景 | 主角色用参考图，次要角色用 prompt 描述 |
| 用户未提供参考图 | 纯文本 prompt，不保持身份 |

与音色克隆的理念一致：
- 用户提供参考图 → 保持长相
- 用户不提供 → 纯文本生成

## 六、大模型选型与调用策略

### 6.1 模型优先级与可用性

```
第一优先：SenseNova deepseek-v4-flash（6 个账号轮询）
  → 用于叙事分析、插图决策等所有 LLM 任务

第二优先（兜底）：Agnes 2.0 Flash（无限免费）
  → 当 deepseek-v4-flash 所有账号配额用完后自动切换
  → 需要代理 http://127.0.0.1:7890
```

当前可用模型：

| 模型 | 限额 | 当前可用 | 说明 |
|------|------|---------|------|
| **deepseek-v4-flash** | ~500次/5h × 6账号 | ✅ 可用 | 推理强，主用 |
| **sensenova-6.7-flash-lite** | ~1500词/5h × 6账号 | ⏳ 暂不可用 | novelSpeakerV4 在用，等通知后再开 |
| **agnes-2.0-flash** | 无限（免费） | ✅ 兜底 | 512K 上下文，需代理 |

> `sensenova-6.7-flash-lite` 目前被另一个项目（novelSpeakerV4）占用做角色标注，6 卷各占一个账号。等它跑完后会释放，到时候可以再用。

### 6.2 API 配置

**SenseNova（deepseek-v4-flash）：**
- Base URL: `https://token.sensenova.cn/v1`
- 模型名：`deepseek-v4-flash`
- 6 个 API Key 存放在 `config/sensenova_apikeys`
- API 兼容 OpenAI 格式

**Agnes 2.0 Flash（兜底文本模型）：**
- Base URL: `https://apihub.agnes-ai.com/v1`
- 模型名：`agnes-2.0-flash`
- 需要代理 `http://127.0.0.1:7890`

**Agnes Image（生图模型）：**
- 同上 Base URL，`POST /v1/images/generations`
- 模型：`agnes-image-2.0-flash` / `agnes-image-2.1-flash`
- 同样需要代理 `http://127.0.0.1:7890`

### 6.3 Key 轮询策略

不要一个账号用完再切下一个，这样浪费五小时滚动窗口。
正确做法：**每次请求轮流使用不同账号，round-robin 轮询。**

```
请求 1 → account[0] 的 deepseek-v4-flash
请求 2 → account[1] 的 deepseek-v4-flash
请求 3 → account[2] 的 deepseek-v4-flash
...
请求 7 → account[0] 的 deepseek-v4-flash（此时 account[0] 第一轮可能已部分恢复）
```

这样能最大化利用每个账号的滚动窗口。

### 6.4 日志记录

每次 LLM 调用都必须记录以下信息，便于后续 debug：

```json
{
  "timestamp": "2026-07-05T12:00:00",
  "model": "deepseek-v4-flash",
  "account_index": 0,
  "prompt_tokens": 1234,
  "completion_tokens": 567,
  "total_tokens": 1801,
  "tool_calls_count": 3,
  "status": "success"  // 或 "retry" / "fallback" / "error"
}
```

### 6.5 错误处理与重试

| 错误类型 | 处理方式 |
|---------|---------|
| tool_call 应该返回却没返回 | 重试，提示模型必须调用工具 |
| API 返回 429（限流） | 等几秒换下一个账号重试 |
| 账号配额用完 | 轮询到下一个账号 |
| 所有 deepseek-v4-flash 都用完 | fallback 到 Agnes 2.0 Flash |
| Agnes 也失败 | 报错停止，不静默忽略 |
| 网络错误 | 重试 3 次，指数退避 |

### 6.6 关于 Tool Calling

使用 `tool_choice="auto"`（默认值）能稳定返回 `tool_calls`。
不要用 `tool_choice="required"`，它不保证给 `tool_calls`。

## 七、跟现有流水线的集成

```
novel-voice-cast 流水线：
  bgm_segmenter.py 场景分割数据
  └── 场景列表（情感标签、时间线、角色）
       └── 插图 Agent（本方案）
            ├── 叙事分析（deepseek-v4-flash）
            ├── 插图决策（deepseek-v4-flash）
            └── prompt 生成（sensenova-6.7-flash-lite）
                 └── 调用生图 API（PuLID / Agnes）
                      └── 输出到 output/illustrations/
```

复用现有数据：
- `bgm_segments.json` 中的场景分割结果可以直接作为插图 Agent 的输入
- `docs/角色卡.md` 中的角色描述用于 prompt 组装
- 情感标签用于控制画面氛围

## 八、需要进一步确认的问题

1. **插图密度**：一卷小说最终多少张图合适？10 张？20 张？需要实测一卷小说后确定
2. **角色参考图管理**：多角色时如何管理参考图？一个角色多张参考图（不同角度/服装）？
3. **插图与音频时间轴关联**：插图在听书时什么时候展示？场景开始时？固定间隔？
4. **回退策略**：如果 LLM 分析失败或生图 API 超时，怎么处理？
5. **成本控制**：Agnes 免费但慢（30s+/张），PuLID 快但需要 4090 服务器。在批量生成时如何选择？
