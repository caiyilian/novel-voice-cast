# Novel Voice Cast 桌面版实施方案

本文是 GitHub Issue #110 的实施与验收基线。桌面版的目标不是重写现有流水线，而是为已经稳定运行的 13 阶段 Python CLI 提供一个安全、可观察、可停止、可恢复、可打包的 Windows 图形入口。

## 1. 已确认的现状

### 1.1 后端流水线

`scripts/run_full.py` 是唯一的全流程入口，依次执行：

1. `parse`
2. `gender`
3. `emotion`
4. `performance`
5. `tts`
6. `splice`
7. `bgm-segment`
8. `bgm-label`
9. `bgm-generate`
10. `bgm-mix`
11. `illustration-plan`
12. `illustrations`
13. `video`

各阶段已经通过 JSON checkpoint、输出文件指纹和 `output/run_full_manifest.json` 支持续跑。桌面版必须直接启动这个脚本，不能增加一个常驻 HTTP 后端，也不能复制一套流水线逻辑。

### 1.2 输入与配置

用户至少选择两份 UTF-8 文本：

- 小说原文 `novel.txt`；
- 与显式对话逐条对应的角色标注 `labels.txt`。

模型、API Key、VoxCPM、ACE-Step、文生图、FFmpeg 和输出目录继续由现有 `config/config.yaml` 及相关密钥文件管理。桌面端只为本次运行覆盖小说与 labels 路径，不改写用户的 YAML。

### 1.3 OpenCode Desktop 可复用原则

参考 `E:/projects/opencode/packages/desktop/ARCHITECTURE.md` 和同目录构建配置，采用下列边界：

- Electron 主进程负责窗口、原生文件选择器、Python 子进程和系统路径操作；
- preload 只通过 `contextBridge` 暴露明确列出的类型安全 API；
- SolidJS 渲染进程只能访问 `window.novelVoiceCast`，不直接访问 Node.js；
- `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`；
- 使用 electron-vite 构建 main、preload、renderer 三部分；
- 使用 electron-builder 生成 Windows NSIS 安装包。

## 2. 范围与非目标

### 2.1 必须完成

- 拖放或原生选择器选择小说与 labels，并显示文件名和绝对路径；
- 两份输入都有效前禁止开始；
- 一键启动完整 13 阶段；
- 显示当前阶段、阶段进度、当前操作/命令和实时日志；
- 支持停止，行为与命令行 Ctrl+C 等效，保留 checkpoint；
- 支持用相同输入和配置继续运行，也支持选择起始阶段；
- 显示总耗时、各阶段耗时、最终产物路径，并能打开输出目录；
- 提供小型样例和自动化测试；
- 能构建并生成 Windows 安装包。

### 2.2 本次不做

- 不把 Python 流水线改造成 Web 服务；
- 不在桌面端重新实现模型推理、缓存校验或编排；
- 不把大模型权重、VoxCPM、ACE-Step 或 Python 虚拟环境打进安装包；
- 不在桌面端显示、复制或上传 API Key；
- 不启动全卷小说作为自动化测试。

桌面应用是项目工作区的伴侣程序。它从项目根目录解析 `.venv/Scripts/python.exe`、`scripts/run_full.py` 和 `config/config.yaml`。打包版允许通过环境变量或设置指定项目根目录，但仍使用该工作区已有的 Python 和模型环境。

## 3. 总体架构

```text
SolidJS Renderer
  │ window.novelVoiceCast（白名单 API）
  ▼
Preload / contextBridge
  │ ipcRenderer.invoke / on
  ▼
Electron Main
  ├─ 原生文件选择器与拖放路径解析
  ├─ PipelineController 状态机
  ├─ child_process.spawn(.venv/Scripts/python.exe, run_full.py ...)
  ├─ stdout/stderr 结构化事件解析
  ├─ 停止、恢复、日志与耗时汇总
  └─ shell.openPath 打开输出目录
          │
          ▼
scripts/run_full.py
  ├─ 13 阶段
  ├─ checkpoint / manifest
  └─ [STAGE] / [PROGRESS] / [LOG] JSON 行
```

不开放任意命令执行 IPC。Python 可执行文件、脚本、配置、日志和输出路径由主进程根据项目根目录计算；渲染进程只能提交已通过主进程选择或校验的小说、labels 和起始阶段。

## 4. Python CLI 扩展

### 4.1 输入覆盖参数

为 `run_full.py` 增加：

```text
--novel PATH
--labels PATH
--desktop-events
```

`--novel` 和 `--labels` 只覆盖内存中的 `config["novel"]`，绝不写回 `config.yaml`。不传参数时保持原 CLI 行为完全不变。

### 4.2 stdout 结构化协议

启用 `--desktop-events` 后，机器事件使用 UTF-8、单行 JSON：

```text
[STAGE] {"version":1,"stage":"emotion","index":3,"total":13,"status":"running","elapsed_seconds":0.0}
[PROGRESS] {"version":1,"stage":"emotion","current":23,"total":120,"percent":19.17,"operation":"正在标注第 23/120 组情绪"}
[LOG] {"version":1,"level":"INFO","message":"using cached emotion labels","stage":"emotion"}
```

规则：

- 每条事件恰好一行，JSON 使用 `ensure_ascii=False`；
- `version` 初始为 1，方便将来兼容升级；
- `[STAGE]` 至少包含 `stage/index/total/status`；
- `[PROGRESS]` 至少包含 `stage/current/total/percent/operation`；
- `[LOG]` 至少包含 `level/message`，有活动阶段时附 `stage`；
- 事件立即 `flush=True`；
- 普通人类可读日志继续保留；
- 任何不符合协议的输出都作为普通日志显示，不能导致桌面端崩溃；
- 进度不得因重试或缓存回退而倒退；无法获得细粒度计数时显示阶段级 0%/100% 和当前操作。

### 4.3 manifest

现有 manifest 继续作为完成状态的权威来源。事件用于实时显示，manifest 用于进程退出后的最终核验和耗时/产物恢复。桌面端不能仅凭退出码宣称成功：退出码为 0 且 manifest `run_status == "complete"` 才算完成。

## 5. Electron 进程与 IPC 设计

### 5.1 IPC 白名单

| 通道 | 方向 | 用途 |
|---|---|---|
| `dialog:pick-text-file` | renderer → main | 选择小说或 labels |
| `file:path-for-drop` | renderer → preload | 用 `webUtils.getPathForFile` 解析拖放文件 |
| `pipeline:get-state` | renderer → main | 获取当前状态快照 |
| `pipeline:start` | renderer → main | 启动完整或指定起点的流程 |
| `pipeline:stop` | renderer → main | 请求优雅停止 |
| `pipeline:event` | main → renderer | 推送阶段、进度、日志和结果 |
| `output:open-directory` | renderer → main | 打开已知输出目录 |

所有 `invoke` 参数在主进程再次校验。文件必须存在、是普通 `.txt` 文件并能读取。起始阶段必须属于固定的 13 阶段枚举。输出目录只能是控制器当前运行所解析的目录。

### 5.2 BrowserWindow 安全设置

```ts
webPreferences: {
  preload,
  contextIsolation: true,
  nodeIntegration: false,
  sandbox: true,
}
```

同时：

- 拒绝任意新窗口；
- 外链只允许显式交给系统浏览器；
- 导航只允许开发服务器或打包后的本地页面；
- 拒绝未列入白名单的权限请求；
- renderer 不接收 `child_process`、`shell`、`fs` 或原始 `ipcRenderer`。

## 6. PipelineController 状态机

### 6.1 状态

```text
idle → starting → running → stopping → interrupted
                         ├────────────→ failed
                         └────────────→ completed

interrupted/failed/completed → starting（重新运行或续跑）
```

快照包含：

- `status`；
- 当前 stage/index/percent/operation/command；
- 13 个阶段各自状态与耗时；
- 总开始时间、总耗时；
- 日志尾部；
- PID、退出码、错误；
- manifest 路径、输出目录和最终产物。

### 6.2 启动命令

默认：

```text
.venv/Scripts/python.exe -u scripts/run_full.py
  --config config/config.yaml
  --novel <selected novel>
  --labels <selected labels>
  --stream-tts
  --desktop-events
  --log <run-specific UTF-8 log>
```

选择续跑起点时追加 `--from-stage <stage>`。命令以参数数组传给 `spawn`，不用 shell 拼接，避免空格、中文路径和命令注入问题。

### 6.3 停止

1. 只向当前控制器持有的 Python PID/进程组发送中断，不扫描或停止其他 Python 任务；
2. POSIX 发送 `SIGINT`；Windows 首选向新进程组发送 Ctrl+Break/SIGINT 等效请求；
3. 等待宽限期，让 `run_full.py` 写入 interrupted manifest 并停止其 streaming TTS 子进程；
4. 超时后只终止本次子进程树；
5. UI 保持“正在停止”，直到进程确实退出；
6. 再次启动使用原输入、配置和 checkpoint，不删除缓存。

正在独立运行的角色换音色、文生图或其他 Python 进程不属于控制器，绝不能受影响。

### 6.4 恢复

“继续运行”默认重放同一条完整命令，让后端自行验证 checkpoint；高级选项允许用户选择 `--from-stage`。恢复前展示 dry-run 缓存检查结果或至少明确当前起点。桌面端不猜测、修改或删除 checkpoint。

## 7. SolidJS 界面

单窗口三段布局：

1. 顶部输入区：两个文件卡片，支持点击“+”和拖放；显示文件名、绝对路径、有效/错误状态。
2. 中央执行区：开始/停止/继续按钮，当前阶段大进度条，13 阶段状态列表，当前操作与实际命令摘要。
3. 底部详情区：实时日志、总耗时、阶段耗时、错误说明、最终产物路径和“打开输出目录”。

交互要求：

- 两份有效输入之前开始按钮禁用；
- 运行期间不能再次启动；
- 停止按钮只在 starting/running 时可用；
- interrupted/failed 状态提供继续按钮；
- 日志默认自动滚动，可暂停自动滚动和清空屏幕显示，但不删除磁盘日志；
- 长路径可复制，界面不能因中文或超长路径溢出；
- 颜色不能作为唯一状态信号，必须同时显示文字/图标。

## 8. 结果与耗时

完成或失败后读取 `run_full_manifest.json`，展示：

- 总状态和总耗时；
- 每个所选阶段的 `status/elapsed_seconds`；
- manifest 中记录的 artifacts；
-常用最终产物：无 BGM 音频、带 BGM 音频、横屏视频、竖屏视频；
- 输出目录和 manifest 路径。

路径存在时可在资源管理器中打开；不存在时按钮禁用并显示原因。不得把“子进程退出”错误地等同为“流水线完成”。
