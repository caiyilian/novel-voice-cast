> 供其他 LLM 审阅。项目：novel-voice-cast（中文轻小说有声书生成流水线）
> 时间：2026-09-24　报告人：AI 助手

## 一、任务背景

把一部中文轻小说（《狼与香辛料》第一卷）转成有声书，全流程自动化：

```
解析 → 性别识别 → 表演指导生成 → TTS合成 → 拼接 → BGM分段 → BGM标注 → BGM生成 → 混音
```

**TTS 引擎**：CosyVoice 3（Fun-CosyVoice3-0.5B），零样本音色克隆。
**规模**：3026 句，其中旁白 1686 句。

**技术栈要点**：
- 表演指导由 LLM 生成，产出 `performance_control` 字段（平均 82 字的中文导演散文）
- 该字段通过 `inference_instruct2(text, instruct, ref_audio)` 的 **instruct 参数**传给 CosyVoice
- 参考音频决定音色，instruct 决定表演风格

## 二、用户反馈的两个问题

1. **旁白不够严肃**——用户希望旁白始终保持严肃一致
2. **控制词被念出来**——例如罗伦斯初遇赫萝处（原文 L290）听到了「放平推进」「留半拍等赫萝接话」等指导语

## 三、已查明的机制（源码级）

### 3.1 控制词泄漏的机制

`E:/projects/cosyvoice/cosyvoice/llm/llm.py:476-498`：

```python
text = torch.concat([prompt_text, text], dim=1)   # instruct 与正文【拼成同一序列】
text_len += prompt_text_len
lm_input = torch.concat([sos_emb, text_emb, task_id_emb, prompt_speech_token_emb])
min_len = int((text_len - prompt_text_len) * min_text_ratio)
```

- `instruct` 被当作 `prompt_text`（前文），与正文**拼接成连续序列**
- `<|endofprompt|>`（token 151646）只是**软分隔符**，不是硬边界
- 模型自回归生成时，若判断「前文未结束」，就会**继续念 instruct**
- **因此泄漏是概率性的**（受 top_k 采样影响）

### 3.2 官方 instruct 用法

`E:/projects/cosyvoice/cosyvoice/utils/common.py:28` 的 `instruct_list`：
```python
"请用广东话表达。"
"请用尽可能快地语速说一句话。"
"请非常开心地说一句话。"
```
全部是 **10-20 字的极短祈使句**。

## 四、我做的实验与结论

### 实验 1：长度扫描（否证「长度假说」）

同一句正文，instruct 长度 10→100 字：

| 字数 | 10 | 21 | 40 | 60 | **82** | 100 |
|---|---|---|---|---|---|---|
| 音频时长 | 7.8s | 6.3s | 7.5s | 6.6s | **22.4s** | 6.4s |

→ **与长度无单调关系**（82 泄漏、100 正常）

### 实验 2：确定性验证（证明概率性）

同一 instruct 重复 5 次：`23.2 / 9.4 / 8.5 / 10.4 / 9.7s` → **随机**

### 实验 3：语义形态（5 次/组）

| 形态 | 字数 | 泄漏率 |
|---|---|---|
| A 叙述散文（项目原版） | 117 | **4/5 = 80%** |
| B 元指令祈使句 | 22 | **0/5 = 0%** |
| C 元指令 + 声学约束 | 51 | **0/5 = 0%** |
| D 纯声学参数（无主语） | 39 | **4/5 = 80%** |

→ 决定因素是**语义形态**（`请用……说这句话` 这类元指令最安全）

### 实验 4：重跑验证

拿 5 句实测泄漏的句子，新旧 instruct 各重跑 3 次 → **30/30 全部干净**
→ 说明**泄漏可随机自愈**，重跑是最简单有效的修复

### 实验 5：采样参数（否证「调 temperature」假说）

**动机**：用户提问「能否通过修改 temperature 参数反复重试解决泄漏」。

**先查源码，发现 CosyVoice 根本没有 temperature**。采样链路是：

```python
# cosyvoice/utils/common.py:138
def ras_sampling(scores, tokens, sampling, top_p=0.8, top_k=25, win_size=10, tau_r=0.1):
    top_ids = nucleus_sampling(scores, top_p=top_p, top_k=top_k)   # top-p + top-k 截断
    if 重复检测触发:
        top_ids = random_sampling(...)                            # 兜底随机

def nucleus_sampling(scores, top_p=0.8, top_k=25):
    ...
    top_ids = indices[prob.multinomial(1, replacement=True)].item()   # multinomial 随机抽取
```

注意 `inference(..., sampling=25)` 的 `sampling` **名字有误导性**——它只在
「检测到重复」的兜底路径使用，不是温度。采样函数由 `cosyvoice3.yaml:32`
（`!name:cosyvoice.utils.common.ras_sampling`）注入，可在运行时替换。

**实验设计**：用**原始散文 instruct**（已知会泄漏的那批，而非已改写的元指令，
否则分不清是采样参数还是提示词起作用），3 句 × 3 次 × 4 组参数。

| 采样参数 | 泄漏率 |
|---|---|
| A 默认 `top_p=0.8, top_k=25` | **3/9 = 33%** |
| B 收紧 `top_p=0.6, top_k=10` | **3/9 = 33%** |
| C 很紧 `top_p=0.3, top_k=3` | **3/9 = 33%** |
| D **贪婪** `top_p=0.01, top_k=1` | **3/9 = 33%** |

**结论：连 `top_k=1`（完全贪心、零随机）都仍是 33%，采样参数对泄漏率毫无影响。**

**更关键的观察**：泄漏与**句子强相关**，与参数无关——
- `idx 20` 在**全部四组**里都泄漏（9/9）
- `idx 21`、`idx 525` 在所有组里基本不泄漏

**为什么必然如此**：回到根因 `llm.py:476`——instruct 与正文被拼成同一序列，
模型判断「该不该结束」看的是**语义**而非随机性。`idx 20` 的 instruct 以
「…四字短促笃定收尾。」结尾，是**完整的陈述句**，模型读起来就是「正文还没念完」，
因此贪心解码也会继续念。

**因此**：
- ❌ 调 temperature / top_p / top_k → **无效**
- ✅ **原样重试** → 有效（实验 4：30/30）
- ✅ **改写为极简元指令** → 最有效（7.5 节：6/6，覆盖率 1.00）

## 五、★ 真正的大 bug：worker 只取 chunks[0]

**这是本次排查最重要的发现，与上述所有实验无关。**

`backend/cosyvoice_worker.py:121`（修复前）：
```python
chunks = []
for item in model.inference_instruct2(task["text"], instruct, task["reference_audio"], stream=False):
    chunks.append(item["tts_speech"])
speech = chunks[0]        # ← 只取第一块，其余全部丢弃！
```

CosyVoice 前端 `split_paragraph(token_max_n=80)` 会把长文本**切成多块**逐块 yield。
worker 只取 `chunks[0]` → **所有超长句子的后半段被静默丢弃**。

### 实测证据（修复前 → 修复后，用 ASR 覆盖率衡量）

| idx | 原文字数 | 修复前覆盖率 | 修复后覆盖率 |
|---|---|---|---|
| 698 | 243 | **0.26** | **1.09** |
| 425 | 162 | **0.32** | **1.00** |
| 1316 | 291 | **0.32** | **0.99** |
| 852 | 164 | **0.33** | **1.00** |
| 1474 | 182 | **0.35** | **1.00** |

**修复**：
```python
if len(chunks) == 1:
    speech = chunks[0]
else:
    import torch
    speech = torch.cat(chunks, dim=-1)   # 拼接全部块
```

### 这解释了之前的「怪现象」

- **长句问题率 28.3% vs 短句 3.4%** —— 只有超过切分阈值的句子才分块
- **「重跑 ASR 无改善」** —— 内容真的不在音频里
- 我曾误判为「截断是概率性的」，实际是**确定性的**（只要分块就必丢）

## 六、我建的检测闭环

### 6.1 脚本清单

| 脚本 | 作用 |
|---|---|
| `scripts/tts_quality_loop.py` | 三段式：`transcribe`（ASR）/ `audit`（LLM判定）/ `repair`（改提示词+重生成） |
| `scripts/tts_fix_loop.py` | 串联上述三段的循环驱动器（最多 N 轮） |
| `scripts/tts_leak_detect.py` | 字符级比对（**已降级为参考**，不作判据） |

### 6.2 ASR 方案

- `faster-whisper` **large-v2**（large-v3 的 HF 缓存不完整，缺 model.bin）
- 模型路径：`E:/huggingface_models/hub/models--Systran--faster-whisper-large-v2/snapshots/f0fe81560cb8b68660e564f55dd99207059c092e`
- 输出**繁简混杂**，用 `opencc-python-reimplemented` 归一

### 6.3 LLM 判定提示词（核心）

输入三份材料：A 原文、B 控制词、C ASR 转录（+ D 字符指标作参考）。
三分类判定：`OK` / `LEAK`（控制词泄漏）/ `MISMATCH`（内容缺失或大幅不符）。

**关键设计**：明确告诉 LLM「短句被 ASR 识别成乱码属于识别失败，不算问题」，
因为字符级指标对短句会严重误报（`嗯。`→`bybwd6` 曾被判泄漏，108 条 <5 字几乎全误报）。

### 6.4 修复提示词（核心规则）

要求 LLM 重写控制词时：
1. **必须以元指令开头**（`请用……的语气说这句话`）——实验证明这是关键
2. 禁止叙述性/对白化表述（「等某人接话」「交棒」）
3. 保留原表演意图

### 7.5 ★ 极简指令验证（重要发现）

对这 6 条**跳过 LLM 改写，直接用极简元指令**：

```
旁白: 请用平稳冷静的叙述语气说这句话。语速适中，句末自然收住。
对话: 请用自然对话的语气说这句话。语速适中，句末自然收住。
```

重生成结果：**6/6 全部成功**，ASR 覆盖率全部 **1.00-1.01**，**无任何泄漏内容**。

对比这 6 条原来的 instruct（94-127 字的详细导演散文），说明：

> **极简元指令（约 25 字）不仅消除泄漏，还完全保留了正文内容。**
> 而详细的表演参数描述（「如马车匀速行进」「带一线了然即敛」）
> 既不保证效果，反而是泄漏的来源。

**这直接回答了「instruct 该简化到什么程度」**：可以简化到只剩「元指令 + 语速/收尾」，
不需要保留逐字的重音/停顿/情绪描述。

**副作用待评估**：表演细节减少，语音的抑扬顿挫可能变得平淡。
但考虑到：
- 用户的原始需求之一是「旁白保持严肃一致」——极简指令天然满足
- 详细 instruct 带来的泄漏风险远大于其表演收益
- 参考音频本身已携带音色与基本语气

**倾向结论**：全量改用极简元指令。

## 八、当前发现的问题（请审阅）

### 问题 1：元指令形态只降低概率，不能根除泄漏

第二轮修复后，LEAK 中只有 **3/140** 的 instruct 是元指令形态（其余 137 条因重写失败未改）。

但即使改成元指令形态，**仍有泄漏报告**。例如 idx 21：
```
instruct: 请以从容平稳的语气说这句话。语速不疾不徐，音量平稳；句号处稍停半拍；
          五个小时放缓匀开；立刻动身稍提即收；末句沉稳放平，如马车匀速行进。
泄漏内容: 「如马车匀速行进」被念出
```
注意：泄漏的是 **instruct 后半段的参数描述**，不是开头。

**疑问**：是否说明「元指令开头 + 后续详细参数」的组合仍会被当正文续写？
是否需要**彻底简化 instruct**（只保留元指令 + 3-5 个关键词，总长 ≤30 字）？

### 问题 2：LEAK 与 MISMATCH 的修复策略是否需要区分？

- **MISMATCH**（内容缺失）→ chunks bug 修复后基本解决，靠**原样重跑**即可
- **LEAK**（控制词泄漏）→ 随机性，**重跑或改提示词**都可能有效

当前 `repair` 对所有非 OK 都走「改提示词 + 重生成」。
**疑问**：是否应该改成「先原样重跑一次，失败再改提示词」？（成本更低，且实验 4 证明重跑常有效）

### 问题 3：旁白「不够严肃」（原始需求，尚未解决）

`performance_profiles.json` 里旁白的 profile 明确写了：
> **baseline_delivery**: "不疾不徐、沉着平稳的文学散文叙述…**不戏剧化、不渲染**"
> **acting_constraints**: "**一切情感须经克制的叙述语调处理**"

但实测：**38.8%（654/1686）的旁白 instruct 含「会心/莞尔/调侃/促狭/俏皮/含笑」类词**。

例：
```
L486: "...压一线干幽默即敛..."
L487: "...刻意轻咬半拍带会心..."
L489: "...得意透出一线含笑了然即敛..."
```

**疑问**：这是 LLM 把 profile 的「温和诙谐」**过度演绎成「活泼俏皮」**了吗？
是否应该在表演指导生成的 prompt 里加硬约束——「旁白禁用情绪色彩词，只描述语速/停顿/音量」？

## 九、待决事项

### 9.1 核心结论（已由实验支撑）

**极简元指令是最优解**（7.5 节实测 6/6 干净，覆盖率 1.00）：

| 方案 | 长度 | 泄漏率 | 内容完整 |
|---|---|---|---|
| 详细导演散文（原版） | 82-127 字 | 80% | ✅ |
| 元指令 + 声学参数 | 51 字 | 0%（单次实验） | ✅ |
| **极简元指令** | **~25 字** | **0%（6/6）** | **✅ 覆盖率 1.00** |

**三种干预手段的有效性**（按实测）：

| 手段 | 有效性 | 依据 |
|---|---|---|
| 调 temperature / top_p / top_k | ❌ **无效**（33% 不变，贪婪解码同样泄漏） | 实验 5 |
| 原样重试 | ✅ 有效（30/30） | 实验 4 |
| 改写为极简元指令 | ✅✅ 最有效（6/6，覆盖率 1.00） | 7.5 节 |

→ **推荐组合**：极简指令治本 + 重试兜底（即 `tts_fix_loop.py` 现有流程）。

### 9.2 待用户决策

1. **是否全量改用极简元指令重跑？**
   - 代价：3026 句全量重生成（约 3-5 小时，本机 2 worker）

## 十一、我的自我批评

**我走了很多弯路**：

1. 一开始用「导演术语命中表」做初筛 → 短句误报严重，**规则永远追不上现实**
2. 提出「长度假说」「措辞假说」→ 都被实验否证
3. 花了大量时间做 prompt 实验，**而真正的 bug 是一行 `chunks[0]`**

**教训：应该先读代码，再做实验。** 实验设计得再精巧，也替代不了对调用链的审查。

用户也明确批评过：「感觉有一种打补丁的感觉…我觉得应该要配套一个语音转文字，
然后每一句生成的语音都要有对应的语音转文字记录，这样就能快速判断哪一句可能有问题。
然后可以让一个大模型看一下原文以及控制词以及转出来的文字，判断一下…」
—— 这个方向是对的，我已按此建了闭环。
