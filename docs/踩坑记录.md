## 3. 踩坑全记录

### 3.1 bf16 模式（23GB 模型 on 24GB 显存）

**问题：** FLUX.1-dev 在 bf16 下占用约 23 GB，RTX 4090 显存 23.64 GB，理论勉强能放。

**尝试的方法：**

| 方法 | 结果 | 原因 |
|------|------|------|
| 直接 `model.to(device)` 放到 GPU | ❌ OOM | 模型 23GB + 激活内存 > 24GB |
| 缩小分辨率到 256×256 | ❌ OOM | 模型本身已占 23GB，仅剩 0.5GB 给激活 |
| 逐块 offload（一次只移一个 block 到 GPU） | ⚠️ 双 blocks 通过，单 blocks OOM | 单 blocks 处理 concat(img, txt)，激活更大 |
| 使用其他 GPU（cuda:2，空载 23.6GB） | ❌ 同上 | 模型本身占满，激活无空间 |

**结论：** 24GB 显存无法运行 FLUX.1-dev 的 bf16 模式。

### 3.2 fp8 量化模式（12GB 模型）

**问题：** 用 `optimum-quanto` 将模型量化到 fp8（12GB），期望在 24GB 上留下 12GB 给激活。

**遇到的困难：**

| 困难 | 解决方式 |
|------|---------|
| JIT 编译 CUDA 扩展需 `Python.h`，系统未装 `python3.10-dev` 且无 root 权限 | 从 Anaconda 缓存的 Python 头文件复制到 venv 下 |
| CUDA 11.5 的 nvcc 不支持 RTX 4090（sm_89） | 切到 `/usr/local/cuda-12.4/bin/nvcc` |
| JIT 编译仍失败（找不到 `Python.h`） | 手动编译所有 `.cu`/`.cpp` 文件，生成 `quanto_cuda.so`，修改 `extension.py` 加载预编译库 |

**最终结果：**

| 方法 | 结果 | 原因 |
|------|------|------|
| fp8 + `model.to(device)` 放到 GPU | ❌ OOM | 模型 12GB 正常，但 `qbytes_mm` 函数在矩阵乘法时执行 `weights * scales`，生成 bf16 权重复制（12GB），临时总内存达 23GB+ |
| fp8 + 逐 block offload | ❌ 报错 | `nn.Module.to()` 在新版 PyTorch 中使用 `swap_tensors`，与 quantized tensor 不兼容 |

**结论：** `optimum-quanto` 的 fp8 实现并非"直接使用 fp8 矩阵乘法核"，而是保留 fp8 权重，每次计算时反量化到 bf16 再乘。这导致实际峰值显存仍然是 bf16 的大小。

### 3.3 最终结论

> **FLUX.1-dev（12B 参数）不适用于 24GB 显存的 GPU。**
>
> 即使在 fp8 量化下，`optimum-quanto` 的实现方式使其峰值显存需求仍接近 bf16 的 23GB，超过 24GB 可用容量。

## 4. 后续建议

| 方案 | 说明 |
|------|------|
| **换用 48GB+ 显存的 GPU**（如 A6000、A100、RTX 6000 Ada） | 所有代码已写完，直接 `bash no_ref.sh` 即可运行 |
| **换用更小的基座模型**（如 SDXL、SD3.5-Medium） | 需重新选型，PuLID 也支持 SDXL |
| **换用其他 fp8 kernel**（如 bitsandbytes、TensorRT-LLM） | 可避免反量化问题 |

### 如果将来换到更大显存的机器

```bash
# 有参考图
bash with_ref.sh /path/to/ref.jpg "your prompt" output.png cuda:0

# 无参考图
bash no_ref.sh "your prompt" output.png cuda:0
```

所有环境配置和模型均已就绪，换机器后直接运行即可。
